# ADR-0004: Authentication with Better Auth, mounted in the NestJS API

- Status: Accepted
- Date: 2026-10-16

## Context
Phase 1 needs sign up / login with email + password and with Google, for a self-hostable app
whose business API is NestJS (`apps/api`) and whose UI is Next.js (`apps/web`). Constraints:

- Self-host first: no hosted identity service; everything runs from `docker compose up`.
- EU-first: no data or telemetry leaves the instance.
- Provider credentials are encrypted at rest and never logged (CLAUDE.md).
- The API never waits on external providers inside a request, except OAuth callbacks; emails go
  through BullMQ.
- One maintainer: the security-critical surface we own should be small.

Ecosystem state as of this ADR (versions checked on npm):

- **Better Auth** 1.7.10 (2026-10-15), MIT. Framework-agnostic; email/password, email
  verification, password reset, social sign-in, DB sessions, rate limiting, account linking,
  plugins (2FA, passkeys, SSO) for later. Official Drizzle adapter, peer `drizzle-orm ^0.45.2`.
  Active release cadence with published advisories (e.g. a June 2026 security update; a
  low-severity Postgres rate-limit race fixed in 1.7.7). Telemetry exists and is off by default.
  NestJS integration is community-maintained (`@thallesp/nestjs-better-auth`, one maintainer).
- **Lucia**: the library is deprecated (March 2025) and is now a guide for writing sessions
  yourself. Its companion libraries **Arctic** (OAuth) and **Oslo** (crypto) are deprecated on
  npm too, except `@oslojs/encoding`. A hand-rolled approach today would use `openid-client`
  (6.8.8, maintained) for Google and `@node-rs/argon2` for passwords.
- **Passport**: `passport` 0.7.0 (2023-11) and `passport-google-oauth20` 2.0.0 (2019) have had no
  releases in years; `@nestjs/passport` 12.0.0 (2026-08) is maintained. Passport only does the
  "verify credentials" step: sessions, email verification, password reset, and rate limiting
  are all on us.

## Options

| | Better Auth | Hand-rolled (Lucia-style) | Passport |
| --- | --- | --- | --- |
| Security-critical code we own | Small: config, NestJS guard, hooks | All of it: session tokens, password hashing, verification/reset tokens, OAuth state/PKCE, rate limiting, CSRF | Most of it: everything except the strategy callback |
| Sessions vs JWT | DB-backed opaque sessions in an HttpOnly cookie, revocable; JWT/cookie cache optional | Whatever we build (DB sessions per the Lucia guide) | Whatever we build |
| Google OAuth | Built in: state + PKCE, ID token checks, account linking | `openid-client` (OIDC-certified) + our glue | `passport-google-oauth20`, unmaintained since 2019 |
| Email verification / password reset | Built in, with enumeration protection; we supply the send callback | We build | We build |
| Rate limiting / CSRF | Built in: origin check, Fetch Metadata, SameSite=Lax, per-route limits | We build | We build |
| NestJS fit | Mount its Node handler on Express; our own guard calls `auth.api.getSession` | Native NestJS code | Native (`@nestjs/passport`) |
| Schema control | Owns 4 tables (user, session, account, verification); names, fields and UUID ids configurable | Full control | Full control |
| Maintenance burden | Track a fast-moving dependency and its advisories | Track our own code, with no outside review | Old core plus all the custom parts |
| Lock-in | Medium: its tables and endpoints; data is plain Postgres | None | Low |

Passport is ruled out: the core is stale and it leaves the hard parts to us. The real choice is
Better Auth versus owning everything. For a single maintainer, a widely used library with
public advisories and fast fixes is a smaller risk than an unreviewed implementation of the
same flows.

## Decision
1. Use **Better Auth** (>= 1.7.10, pinned with lockfile), with the official **Drizzle adapter**
   on the existing `pg` pool and our own Drizzle table definitions (snake_case columns, UUID ids
   generated by Postgres).
2. Mount it in `apps/api` directly, not through the community NestJS adapter: Better Auth's
   Node handler serves `/api/auth/*` before Nest's body parser; a global NestJS guard resolves
   the session with `auth.api.getSession()` and an `@Public()` decorator opts routes out
   (public booking pages, health).
3. **Opaque DB sessions**, no JWT: HttpOnly, `Secure` in production, `SameSite=Lax`, 7-day
   expiry refreshed daily (Better Auth defaults). No cookie cache in Phase 1, so revocation is
   immediate.
4. **Same origin**: the browser only talks to the web origin; Next.js rewrites `/api/*` to the
   API. Cookies stay first-party, and Better Auth's origin check uses `APP_URL` as the only
   trusted origin.
5. **Passwords**: argon2id through Better Auth's custom `hash`/`verify` hook (`@node-rs/argon2`,
   OWASP parameters), rather than relying on undocumented default scrypt parameters.
6. **Email verification required** before a session is created. Verification and reset emails
   are enqueued to BullMQ from Better Auth's send callbacks; the request never waits on SMTP.
7. **Rate limiting in Redis**, so limits hold across API instances, through Better Auth's
   `rateLimit.customStorage` with an atomic `consume` (one Lua script: `INCR` + `EXPIRE`).
   Stricter rules on sign-in, sign-up and password reset; `trustedProxies` configured for
   reverse-proxy deployments. Better Auth's `secondaryStorage` is deliberately **not** used:
   configuring it also moves sessions into Redis, keyed by the plain session token (see
   "Token storage findings").
8. **Google login only proves identity.** Scopes `openid email profile`; a database hook strips
   access/refresh/ID tokens from Google login accounts so no provider credential is stored there.
   Google Calendar access is a separate, explicit "connect calendar" flow owned by our code, with
   tokens in `calendar_connections`, encrypted with AES-256-GCM (to be detailed in its own ADR).
9. Account linking: a Google sign-in links to an existing user only when Google reports the
   email as verified and the existing user's email is verified too.
10. Telemetry explicitly disabled (`telemetry: { enabled: false }`, `BETTER_AUTH_TELEMETRY=0`).
11. **Only hashes of tokens are stored** (see findings below):
    - Session tokens: an adapter wrapper around the Drizzle adapter stores SHA-256 (base64url)
      in `sessions.token_hash`. It hashes every `token` value in writes and `where` clauses, and
      returns the raw token only when the caller supplied it (create, or lookup by the cookie
      token). Rows read any other way carry a sentinel instead of a token, and using the
      sentinel in a query throws, so no code path can silently fall back to a wrong match.
    - The endpoints that hand stored tokens back to Better Auth or the client (`/list-sessions`,
      `/revoke-session`, `/revoke-sessions`, `/revoke-other-sessions`) are disabled. "Sign out
      other devices" is our own endpoint: delete the user's sessions except the current hash.
    - Verification identifiers: `verification.storeIdentifier: "hashed"` (built in). This covers
      password-reset tokens and OAuth state. Email verification uses a signed JWT, not stored.
12. **Reserved usernames**: names that clash with routes or could impersonate the system
    (`api`, `admin`, `auth`, `health`, `login`, `signup`, `settings`, `dashboard`, `support`,
    `_next`, `www`, `cuckoo`, ...) are rejected. One list in `packages/shared`, enforced by the
    Zod username schema and by the database hook that generates and validates usernames.
13. **No account enumeration**: sign-up, sign-in and password reset return the same status and
    response shape, with comparable timing, whether or not the email exists:
    - sign-up returns a synthetic user for an existing email (built in when email verification
      is required). Better Auth generates UUIDs itself (`generateId: "uuid"`) so synthetic and
      real ids look alike; fields added by our hooks are not returned. An existing account gets
      a "someone tried to sign up" email, enqueued like the real verification email, so both
      paths do the same work;
    - sign-in hashes a dummy password for unknown emails and returns the same 401 as a wrong
      password (built in). `403 EMAIL_NOT_VERIFIED` is only reachable with the correct password,
      so it does not reveal whether an account exists;
    - password reset returns the same message and simulates the lookup (built in); the email
      itself is enqueued, so both paths stay fast.
    Integration tests assert identical responses and bounded timing differences.
14. **Expired sessions and verifications are deleted** by a repeatable BullMQ job in the worker
    (every hour), not by request-time cleanup.

## Token storage findings (better-auth 1.7.10 source)
- `createSession` stores `token: generateId(32)` as is; `findSession` looks it up with
  `where token = <cookie value>`. Session tokens are **stored in plain text**. The session cookie
  is HMAC-signed with `BETTER_AUTH_SECRET`, so a leaked token is not directly usable without the
  secret, but the secret often lives next to the database credentials, hence decision 11.
- With `secondaryStorage`, sessions are written to it keyed by the plain token, together with the
  full user object.
- `/list-sessions` returns stored tokens to the client; `/revoke-other-sessions` reads tokens back
  from the database and deletes by them. With hashed storage these would hand out hashes and,
  worse, silently fail to revoke, which is why they are disabled rather than wrapped.
- Change password and user deletion delete sessions by user id, which hashing does not affect.
- Verification identifiers support `"plain" | "hashed" | { hash }` via
  `verification.storeIdentifier`; reset tokens are stored as `reset-password:<token>` identifiers.

## Consequences
- Four auth tables follow Better Auth's model; schema changes to them go through its expected
  fields. Our domain tables reference `users.id` (UUID) as usual.
- Better Auth releases and advisories must be tracked; Dependabot covers version bumps, and
  upgrades get the integration tests for sign-up, sign-in, Google callback and reset.
- The session-hashing wrapper depends on Better Auth's internal call patterns. Every Better Auth
  upgrade must pass the auth integration tests, which assert that only hashes are stored and that
  sign-in, refresh, sign-out and "sign out other devices" still work.
- Email jobs carry verification and reset links, so these secrets sit in Redis until the job
  runs. Jobs are removed on completion and failed jobs expire quickly; encrypting job payloads
  is to be decided when the email worker is built.
- Tests also cover: stripping Google tokens on create and update, and email normalization to
  lowercase.
- Switching away later means re-implementing the flows but not migrating identities: users,
  password hashes (argon2id) and Google subject ids are plain rows in our database.
